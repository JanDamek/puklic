# DM List Sort by Last Activity — Architect Report (2026-05-24, issue #11)

## Summary

DM list is ephemeral (gateway-driven `DmListOrchestrator`, not persisted), and current upsert appends new entries at the tail — MainScreen.kt:214 flags this as a known stub. Fix is contained: add nullable `lastMessageId: MessageId?` to `DmChannel` domain class, replace append upsert with `sortedByDescending` over `lastMessageId.value` (Discord snowflakes are time-monotonic), and have `DmListOrchestrator` subscribe to `GatewayEventSource.MessageCreated` to bump DMs reactively. No SQLDelight changes; READY's `private_channels[].last_message_id` seeds the field. Preserve-on-null guards partial CHANNEL_UPDATE payloads. Option A (direct gateway subscription) chosen over shared activity bus — no premature abstraction.

## 1. Goal & non-goals

**Goal:** DM list sorted by most-recent activity (last message). New MESSAGE_CREATE reactively bumps DM to top.

**Non-goals (v1):**
- Persisting DMs to SQLite (ephemeral by design — preserve)
- In-guild channel sort (uses Discord `position`)
- Unread / mention badges

## 3. Provenance of lastMessageId

Three signals (verify `DiscordChannelDto.last_message_id` field during Step 6):
1. **READY** → `private_channels[].last_message_id` — initial population
2. **CHANNEL_CREATE / CHANNEL_UPDATE** — same shape; preserve-on-null (`copy(lastMessageId = new ?: current.lastMessageId)`)
3. **MESSAGE_CREATE** — `message.id` becomes new lastMessageId (snowflakes monotonic → sortable as Long)

## 4. Signal architecture — Option A (chosen)

`DmListOrchestrator` subscribes directly to `GatewayEventSource.events`, same source MessageOrchestrator already uses. On `MessageCreated` where `channelId` is in `_dms.value`, call `bumpForMessage`.

**Rejected Option B** (shared "channel-activity" SharedFlow): premature generalization. Extract only if a second consumer (e.g. future guild-channel unread sort) appears.

## 5. Implementation sketch

```kotlin
private fun upsert(channel: DmChannel) {
    _dms.value = (_dms.value.filterNot { it.id == channel.id } + channel)
        .sortedByDescending { it.lastMessageId?.value ?: Long.MIN_VALUE }
}

private fun bumpForMessage(channelId: ChannelId, messageId: MessageId) {
    val current = _dms.value.firstOrNull { it.id == channelId } ?: return
    upsert(current.copy(lastMessageId = messageId))
}
```

`Long.MIN_VALUE` sentinel sinks new empty DMs to bottom — matches Discord behavior.

## 7. Risks (revised per Step 3 critic)

1. **CHANNEL_UPDATE omitting last_message_id** — preserve-on-null lives in `DmListOrchestrator.upsert` (mapper is stateless and can't know current value). Touch list adds `GuildMapper.kt` for reading dto.last_message_id → MessageId.
2. **MESSAGE_CREATE before CHANNEL_CREATE race** — bumpForMessage no-ops; subsequent CHANNEL_CREATE upsert seeds via READY's lastMessageId. Brief stale ordering acceptable v1.
3. **Sort O(N log N) per write** — negligible for <500 DMs.
4. **Nullable MessageId?** — keep nullable; sentinel only in comparator.
5. **`SharedFlow` replay=0** — DmListOrchestrator MUST init at session bootstrap before READY dispatch (same lifecycle slot as MessageOrchestrator). Verify wiring in DependencyGraph + session module.
6. **Stable sort** — Kotlin stdlib `sortedByDescending` is stable on JVM (TimSort), Native, JS. Null-lastMessageId DMs preserve insertion order.

## 7.1 Preserve-on-null IN UPSERT (not mapper) — critic fix

```kotlin
private fun upsert(channel: DmChannel) {
    val previous = _dms.value.firstOrNull { it.id == channel.id }
    val merged = channel.copy(
        lastMessageId = channel.lastMessageId ?: previous?.lastMessageId,
    )
    _dms.value = (_dms.value.filterNot { it.id == channel.id } + merged)
        .sortedByDescending { it.lastMessageId?.value ?: Long.MIN_VALUE }
}
```
