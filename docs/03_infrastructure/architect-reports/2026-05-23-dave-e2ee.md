# DAVE E2EE Voice — Architecture Plan (2026-05-23)

## Summary

DAVE = Discord Audio/Video End-to-End Encryption, built on MLS (RFC 9420) for group key agreement + per-frame ChaCha20-Poly1305 over Opus/video payload. The implementation blocker is the MLS library: `com.wire:core-crypto-jvm:4.2.0` exists on Maven Central and is the only mature Kotlin/JVM MLS, but is **GPL-3.0** + a JNI wrapper around Rust (ships .so/.dylib per platform). Distributed Puklic binary is already GPL-2.0 due to bundled libx264 (Phase 6), so accepting Wire's GPL-3.0 for the same binary is a small step — source stays Apache-2.0, binary becomes GPL-3.0-or-later. Alternative path: wrap Discord's MIT-licensed `libdave` C++ reference via JNI (multi-week native cross-compile pipeline). Acheron source confirms voice gateway DAVE opcodes are 21-31 (not the often-misquoted 14-26).

## 1. Feasibility verdict

**Two viable paths, both nontrivial.**

| Path | Library | License | Effort | Risk |
|---|---|---|---|---|
| **A. Wire core-crypto** | `com.wire:core-crypto-jvm:4.2.0` | GPL-3.0 | 3-4 engineer-weeks | binary distribution becomes GPL-3.0 |
| **B. libdave JNI wrapper** | Discord libdave C++ (MIT) | MIT | 6-8 weeks (build pipeline + JNI + cross-compile) | matches Discord byte-for-byte |
| ~~C. Hand-roll MLS in Kotlin~~ | — | — | 4-6 months + unaudited crypto | DO NOT |

**Path A** is fastest. License delta is acceptable because Puklic's distributed binary is already GPL-2.0 from libx264 (commit 1ff8c58, Phase 6 self-contained refactor). Bumping to GPL-3.0-or-later keeps source under Apache-2.0; only the combined binary distribution changes.

**Path B** is the "correct" long-term answer (matches Discord exactly, permissive license) but blocks DAVE for months. Defer to Phase 3.2.

**Recommendation: Path A with explicit ADR documenting the license decision.**

## 2. Goal & non-goals

**Goal.** Per-frame E2EE on Opus voice frames + later H.264/VP8 video using MLS group key agreement, negotiated over voice gateway opcodes 21-31. Lock icon closed; pairwise fingerprint UI; graceful downgrade when any member doesn't support DAVE.

**Non-goals:**
- Custom MLS ciphersuite — only ciphersuite 1 (`MLS_128_DHKEMX25519_AES128GCM_SHA256_Ed25519`) which Discord uses.
- Out-of-band identity verification beyond fingerprint display.
- Persistent group state across restarts — DAVE groups are ephemeral per call.
- Stage / soundboard / activities encryption.

## 3. Library choice

**Primary:** `com.wire:core-crypto-jvm:4.2.0`
- Brings `core-crypto-uniffi-jvm:4.2.0` (Rust .so/.dylib/.dll per platform classifier)
- Supports MLS ciphersuite 1 (matches Discord)
- Exposes `exportSecretKey(conversationId, label, length)` for DAVE's per-frame key derivation
- GPL-3.0 license

**iOS gap:** `core-crypto-iosarm64` stuck at 0.6.0-rc. Either accept "no DAVE on iOS" or invest in libdave-JNI eventually.

## 4. MLS background (minimum needed)

- **Group state** keyed by `ConversationId` = Discord channelId
- **KeyPackage**: client's public material used by joiners
- **Commits** advance the **epoch**; each epoch derives new **exporter secret** via key schedule
- **Welcomes** install group state at joining epoch
- **Per-frame key**: HKDF(exporter_secret, label=`"Discord Secure Frames v0"` + SSRC + generation) — exact label TBC from libdave headers
- **Pairwise fingerprint**: SHA-256 of concatenated signature public keys, displayed as numeric groups for verbal verification

## 5. DAVE wire protocol (voice gateway, verified from Acheron)

**Opcodes 21-31** (not 14-26 as often cited):

| Op | Name | Dir | Format | Payload |
|---:|---|---|---|---|
| 21 | DAVE_PROTOCOL_PREPARE_TRANSITION | S→C | JSON | `{ protocol_version, transition_id }` |
| 22 | DAVE_PROTOCOL_EXECUTE_TRANSITION | S→C | JSON | `{ transition_id }` |
| 23 | DAVE_PROTOCOL_READY_FOR_TRANSITION | C→S | JSON | `{ transition_id }` |
| 24 | DAVE_PROTOCOL_PREPARE_EPOCH | S→C | JSON | `{ protocol_version, epoch }` |
| 25 | DAVE_MLS_EXTERNAL_SENDER_PACKAGE | S→C | binary | MLS ExternalSender bytes |
| 26 | DAVE_MLS_KEY_PACKAGE | C→S | binary | MLS KeyPackage bytes |
| 27 | DAVE_MLS_PROPOSALS | S→C | binary | MLS Proposals frame |
| 28 | DAVE_MLS_COMMIT_WELCOME | C→S | binary | Commit + optional Welcome |
| 29 | DAVE_MLS_ANNOUNCE_COMMIT_TRANSITION | S→C | binary | Commit + transition_id header |
| 30 | DAVE_MLS_WELCOME | S→C | binary | Welcome message |
| 31 | DAVE_MLS_INVALID_COMMIT_WELCOME | C→S | JSON | `{ transition_id }` |

Binary frame layout: `(seq:u16 BE)(op:u8) || MLS bytes`. Exact bytes need wire capture to confirm.

**Handshake:**
- IDENTIFY (Op 0) carries `max_dave_protocol_version: 1`
- SESSION_DESCRIPTION (Op 4) carries `dave_protocol_version` — server picks min of both
- Transition state machine: PREPARE → C sends READY_FOR_TRANSITION → EXECUTE → swap encryptors

## 6. Per-frame encryption

- **AEAD**: ChaCha20-Poly1305 (DAVE v1)
- **Key per**: (epoch, sender SSRC, generation counter)
- **Encrypted region**: Opus payload only (RTP header + extension + SSRC plaintext for SFU routing)
- **Frame layout**: `[opus ciphertext][tag:16][nonce/gen trailer][magic marker]` — port from libdave headers, do NOT invent
- **Order**: Opus encode → DAVE encrypt (frame key) → write RTP payload → per-hop AEAD (session key) → UDP
- **Decrypt**: reverse; maintain per-(SSRC, userId) decryptor with key ratchet; bounded generation window ~10

## 7. Module structure

New module **`:shared:voice-dave`** (separable so non-E2EE builds can omit):

```
shared/voice-dave/
├── src/commonMain/kotlin/dev/puklic/voice/dave/
│   ├── DaveSession.kt            # high-level enable/disable + transitions
│   ├── MlsClient.kt              # interface around core-crypto
│   ├── FrameEncryptor.kt         # per-SSRC encrypt + key ratchet
│   ├── FrameDecryptor.kt         # per-SSRC decrypt + generation window
│   ├── FrameLayout.kt            # trailer parse/build (libdave-compatible)
│   ├── ExporterDerivation.kt     # HKDF label "Discord Secure Frames v0"
│   ├── PairwiseFingerprint.kt
│   └── gateway/
│       ├── DaveOp.kt             # opcodes 21-31
│       └── DaveBinaryFrame.kt    # binary framing
└── src/jvmMain/kotlin/.../MlsClient.jvm.kt   # core-crypto-jvm impl
```

Wiring:
- `:shared:voice` gains `daveProvider: DaveProvider?` injection. Non-null → CapturePipeline inserts frame-encrypt step before per-hop encrypt; PlaybackPipeline inserts decrypt after per-hop decrypt.
- Voice gateway routing: text frames → current handler; binary frames → `DaveBinaryFrame.dispatch`
- IDENTIFY bumps `max_dave_protocol_version: 1`
- SESSION_DESCRIPTION parsing reads `dave_protocol_version`; >0 → `DaveSession.init(version)`

UI:
- Lock icon state from `DaveSession.state`
- "Verify call" sheet with per-participant pairwise fingerprints

## 8. Migration phases

1. **Phase 3.1a — passive observer** (1 day). Bump IDENTIFY max to 1; `DaveSession` logs 21-31 traffic + sends READY/INVALID to keep gateway happy. Calls remain non-E2EE because we never send KeyPackage.
2. **Phase 3.1b — library spike** (2-3 days). License ADR. Scaffold `:shared:voice-dave`. Integrate core-crypto-jvm:4.2.0. Prove: client init, generate KeyPackage, process Welcome, expose exporter secret.
3. **Phase 3.1c — protocol layer** (3-5 days). Implement opcodes 21-31. Drive transitions. Send KeyPackage on PREPARE_EPOCH. Process Welcome/commits/proposals. Compare against Acheron logs.
4. **Phase 3.1d — frame crypto** (3-5 days). Port FrameLayout + key ratchet from libdave. Wire FrameEncryptor into CapturePipeline behind feature flag.
5. **Phase 3.1e — multi-party correctness** (1 week). 3+ party calls; member joins/leaves mid-call; epoch transitions while speaking; downgrade on non-DAVE joiner. Fingerprint UI.
6. **Phase 3.1f — Android** (when Android voice lands, Phase 3.2+). Swap to `core-crypto-android`. iOS deferred.

**Total estimate:** 3-4 engineer-weeks once licensing is unblocked.

## 9. Risks (max 5)

1. **Cryptographic correctness.** Any HKDF label / nonce / key ratchet / epoch bug silently breaks confidentiality. Mitigation: byte-for-byte match libdave reference vectors; informal review before release.
2. **GPL-3.0 contagion.** Already partially in effect (libx264 → GPL-2.0 binary). Bumping to 3.0 is small delta but needs ADR + LICENSE update.
3. **Unstable protocol bytes.** Binary opcode framing + DAVE frame trailer not in Discord public docs — must be inferred from libdave + wire capture. Mitigation: pin DAVE protocol version, downgrade on parse failure.
4. **Multi-member churn.** Frequent commits = epoch thrash = audio dropouts. Mitigation: generation window ≥ 16.
5. **iOS gap.** `core-crypto-iosarm64` at 0.6.0-rc. Accept "no DAVE on iOS" v1.

## 10. Recommendation

**Path A: implement DAVE with `com.wire:core-crypto-jvm:4.2.0`.** Project's binary distribution is already GPL-2.0 (libx264 from Phase 6). Bumping to GPL-3.0-or-later for E2EE voice is a fair trade. Source code remains Apache-2.0.

Concrete sequence:
1. ADR `docs/01_architecture/adr/00XX-dave-licensing.md` documenting GPL-3.0 binary acceptance
2. Update LICENSE-third-party.txt + docs/06_ops/licensing.md
3. Execute phases 3.1a → 3.1e sequentially (3-4 weeks)
4. iOS DAVE deferred to libdave-JNI in future Phase

If GPL-3.0 binary is unacceptable, defer DAVE indefinitely. Discord's protocol allows the call to proceed unencrypted-at-app-layer; per-hop AEAD continues to protect against passive on-path attackers. Other clients show an open padlock.

## 11. Addendum (Phase 3.1c, 2026-05-23) — exporter label gap is structural

While implementing 3.1c (gateway opcodes 21-31 + `DaveSession`), the previous
note in `MlsClient.kt` claiming Wire 4.2.0 uses label `"AVS"` was found to be
wrong. Verified against the upstream Rust source at
`https://github.com/wireapp/core-crypto/blob/v4.2.0/crypto/src/mls/conversation/export.rs`:

```rust
impl MlsConversation {
    const EXPORTER_LABEL: &'static str = "exporter";
    const EXPORTER_CONTEXT: &'static [u8] = &[];
    ...
}
```

Both the public Wire API (`CoreCryptoContext.deriveAvsSecret(id, len)`) and the
lower `uniffi.CoreCryptoContext.exportSecretKey(id, len)` take only
`(conversationId, keyLength)` — no label, no context. The Rust FFI exposes no
labelled exporter symbol at all. Inspected newer releases up to 9.3.4: same
signature, same hardcoded label. Reflection is therefore not a workaround; the
fix is either upstream Wire patch or libdave-JNI.

**Decision for 3.1c.** `MlsClient.exportSecret(groupId, label, context, length)`
gained label + context parameters and now applies a local HKDF-Expand on top of
Wire's `"exporter"` PRK (info = label || context, RFC 5869). Properties:

| property | behaviour |
|---|---|
| label-sensitive locally | yes (HKDF info changes) |
| context-sensitive locally | yes (HKDF info changes) |
| per-epoch fresh | yes (Wire's exporter advances per Commit) |
| wire-compatible with Discord/other DAVE clients | NO — Wire's MLS-Exporter PRK uses label "exporter" not "Discord Secure Frames v0", and the label feeds the MLS key schedule itself, so PRKs differ |

This means Puklic + Puklic-only calls would interop on the test channel; Puklic
↔ Official Discord clients would NOT — frame keys diverge after MLS exporter.
Acceptable for 3.1c (gateway plumbing) since byte-correct frame interop is the
explicit goal of Phase 3.1d/3.2.

## 12. Phase 3.1c landed (2026-05-23)

Module additions to `:shared:voice-dave`:
- `gateway/DaveOp.kt` — opcodes 21-31 named constants
- `gateway/DaveBinaryFrame.kt` — `(seq:u16 BE)(op:u8)||payload` parse + write
- `DaveSession.kt` — state machine (Idle → Initialized → PreparingTransition →
  Active; Reinitializing; Disabled) driving the MLS handshake via injected
  send-binary / send-json callbacks. Exposes `deriveFrameKey(ssrc, generation)`.

`MlsClient` gained:
- `processCommit(groupId, handshakeBytes)` — routes opcodes 27 + 29 into Wire's
  `decryptMessage`.
- `processExternalSender(channelId, bytes)` — no-op placeholder; Wire 4.2.0
  cannot retrofit an external sender post-`createConversation`. Tracked.
- `exportSecret` now takes `context: ByteArray`; see addendum §11.

Tests added: `DaveBinaryFrameTest` (parse/write round-trip + short-frame null +
big-endian header), `DaveSessionTest` (8 cases covering PREPARE_TRANSITION
supported/unsupported version, PREPARE_EPOCH KeyPackage emit, EXECUTE_TRANSITION
post-Welcome, INVALID_COMMIT_WELCOME re-init, WELCOME storing groupId,
processCommit dispatch, deriveFrameKey null pre-join, deriveFrameKey
label+context+length). Smoke test extended to verify exporter label-sensitivity
and context-sensitivity.

NOT in 3.1c (deferred to 3.1d): integration into `DefaultVoiceClient` (requires
voice-gateway transport extension for binary WS frames + an `OnDaveJson` /
`OnDaveBinary` dispatcher; also requires `processExternalSender` to be effective
which needs the Wire upgrade / libdave path). The 3.1c module is shippable as a
standalone unit and unblocks 3.1d once the transport extension lands.

## 13. Phase 3.2 — libdave JNI wrapper landed (2026-05-23)

Switched to Path B (libdave JNI) per user direction. Discord's MIT-licensed
`libdave` C++ reference compiled on macOS arm64 against OpenSSL 3 + mlspp via
vcpkg (built `libdave.dylib`, 4.3 MiB, self-contained — only `libSystem` +
`libc++` dynamic deps). The library already ships a flat C API
(`cpp/includes/dave/dave.h`, 43 exported `dave*` symbols), so no C++ shim was
needed; JNA binds the symbols directly.

Module additions to `:shared:voice-dave`:
- `LibdaveLoader.kt` — extracts the bundled native lib from JAR resources
  (`/libdave/<os>-<arch>/libdave.{dylib,so,dll}`) to a temp file and
  `System.load`s it. Currently bundles macOS arm64 only.
- `LibdaveBindings.kt` — JNA `Library` interface covering session,
  KeyPackage, Welcome / Commit dispatch, ExternalSender, KeyRatchet,
  Encryptor + Decryptor, pairwise fingerprint, logging.
- `LibdaveMlsClient.kt` — `MlsClient` impl backed by `daveSession*` calls.
  Backend is selected by system property `puklic.voice.dave.backend`
  (`wire` default for now, `libdave` opt-in).

`MlsClient` contract refinements for libdave:
- `init(userId)` returns an empty byte array — libdave's C API does not expose
  the own signature public key (pairwise fingerprint flow takes its place).
- `exportSecret(...)` throws `UnsupportedOperationException` — libdave drives
  per-frame keys through `daveSessionGetKeyRatchet` + `daveEncryptor` /
  `daveDecryptor`, not through a labelled MLS exporter. The architecturally
  correct frame-crypto path is a Phase 3.2 follow-up.
- `processExternalSender(channelId, bytes)` is now effective (libdave supports
  post-hoc attach via `daveSessionSetExternalSender`). This is the structural
  fix vs Wire 4.2.0.
- `currentEpoch(groupId)` is tracked locally (incremented on each successful
  ProcessCommit / ProcessWelcome) because libdave does not expose epoch through
  the C API.

Tests added: `LibdaveMlsClientSmokeTest` — verifies the native library loads,
session can be created + initialized + destroyed without crashing, and
post-hoc external-sender attach succeeds. Tests are gated with
`Assumptions.assumeTrue(isSupportedPlatform())` so non-macOS-arm64 CI runs
skip cleanly rather than fail.

NOT in this phase (deferred to follow-up):
- Linux + Windows native lib builds (need a CI matrix with vcpkg + OpenSSL).
- Full frame-crypto integration: `daveEncryptorCreate` /
  `daveSessionGetKeyRatchet` / `daveEncryptorSetKeyRatchet` /
  `daveEncryptorEncrypt` wired into `CapturePipeline`, and the matching
  decryptor path into `PlaybackPipeline`.
- Pairwise fingerprint UI (uses `daveSessionGetPairwiseFingerprint` callback).
- Default backend flip from `wire` to `libdave` (blocked on the frame-crypto
  integration + multi-platform native lib bundling).
- Discord protocol byte-vector regression tests (would prove byte-for-byte
  interop with the official client; libdave's own test suite covers most of
  this internally, but our adapter needs a focused E2E once the gateway
  transport extension lands).
