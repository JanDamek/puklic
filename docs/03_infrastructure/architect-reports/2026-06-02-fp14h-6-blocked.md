Status: blocked, no code shipped. Issue #62.

## §1 Why FP-14h-6 cannot ship in this session

The master plan §2 lists FP-14h-6 as "Promote `DefaultVoiceClient` from
`:shared:voice/jvmMain` to `:shared:voice-codec/commonMain`. Replace `AtomicInteger` with
`kotlinx.atomicfu.AtomicInt`. Replace `ConcurrentHashMap` (DAVE-only) with non-concurrent
map inside the DAVE factory's own scope."

Audit reveals an unstated prerequisite that FP-14h-2e explicitly deferred. From
`shared/voice-codec/src/commonMain/kotlin/dev/puklic/voice/audio/AudioCapture.kt`:

```
// FP-14h-2e (issue #69): `audioCapture()` and `listAudioDevices()` top-level functions
// live in JavaSoundCapture.kt / JavaSoundDevices.kt as plain JVM functions (not
// expect/actual) until FP-14h-3 ships Apple audio actuals and these get promoted to
// commonMain `expect`. Per architect plan §1.1 deferred items.
```

`DefaultVoiceClient.startPipelines()` calls `audioCapture()` / `audioPlayback()`; the
`init { refreshDevices() }` call hits `listAudioDevices(Direction.Capture/Playback)`. All
three are JVM-only top-level functions today. iOS has `IosAVAudioEngineCapture` /
`IosAVAudioEnginePlayback` classes (FP-14h-3 shipped 5b3fa7d) but **no `expect fun
audioCapture()` / `audioPlayback()` / `listAudioDevices()` declarations in commonMain**.

To move `DefaultVoiceClient` to commonMain we must either:

1. Promote the three top-level functions to `expect fun` in commonMain + add iOS + Mac
   App Store actuals (the deferred work from FP-14h-2e), or
2. Refactor `DefaultVoiceClient` to receive `AudioCapture`, `AudioPlayback` and the
   device list as constructor parameters from the wiring layer.

Option (1) is the architecturally-correct path (matches `H264DecoderFactory`,
`VoiceUdpTransportFactory`, `XChaCha20Poly1305`, `OpusCodec` patterns); option (2) leaks
the orchestration responsibility "open the platform device on this scope" into the DI
graph and would have to be undone once option (1) lands. Per HARD RULE #2, option (1) is
the only path that doesn't introduce a temporary.

Option (1) is bounded but real work:
- `expect fun audioCapture(): AudioCapture` in commonMain
- `expect fun audioPlayback(): AudioPlayback` in commonMain
- `expect fun listAudioDevices(direction: AudioDevice.Direction): List<AudioDevice>` in commonMain
- JVM actuals delegate to existing `JavaSound*` impls
- iOS actuals delegate to `IosAVAudioEngine*` (already present in iosMain) + a new
  `iosListAudioDevices` using `AVAudioSession.availableInputs` (capture) and a stub
  default output for playback (iOS playback device is implicit).
- Mac App Store actuals delegate to the JNA-VT bridges already present in
  `:desktop:platform-macos-appstore`.
- Update every JVM call-site that imports the top-level `audioCapture()` directly
  (currently the JVM-only voice subsystem).

This is its own FP-14h-5.5 slice (~150 LoC + tests, ~1 hour). FP-14h-6 then becomes a
mechanical move once it lands.
